# Python Sockets — TCP Client, UDP Client, TCP Server

> [!info] Why this exists Nmap, Hydra, netcat, reverse shells — all of it is sockets underneath. Building these by hand turns "run the tool" into "understand what the tool is actually doing." This is also the direct foundation for bind/reverse shells later (same server pattern, `subprocess` swapped in for a hardcoded reply).

---

# TCP Client

> [!question] Goal Connect to a real web server (google.com:80), send a proper HTTP request over a raw socket, and read the response back.

```python
import socket

HOST = "www.google.com"
PORT = 80

client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)  # create socket object
client.connect((HOST, PORT))                                 # connect the client

client.send(b"GET / HTTP/1.1\r\nHost: google.com\r\nConnection: close\r\n\r\n")

response = client.recv(4096)
print(response.decode())
client.close()
```

### Line-by-line

- **`socket.socket(socket.AF_INET, socket.SOCK_STREAM)`**
    - `AF_INET` → use IPv4 addressing
    - `SOCK_STREAM` → use TCP (reliable, ordered, connection-based) — as opposed to `SOCK_DGRAM` (UDP)
- **`client.connect((HOST, PORT))`**
    - DNS resolves `www.google.com` → an IP address
    - The TCP **three-way handshake** (SYN → SYN-ACK → ACK) happens automatically at the OS level. By the time this line returns, there's a live, established connection.
- **`client.send(b"...")`**
    - The `b"..."` prefix is a **bytes literal**, not a string. Sockets operate at the byte level — you always send/receive bytes explicitly, never plain text directly.
    - The content is a raw **HTTP request**, built by hand:
        - `GET / HTTP/1.1` — method `GET`, path `/`, protocol version
        - `Host: google.com` — required in HTTP/1.1 (a single IP can host multiple domains, so the server needs to know which one you want)
        - `Connection: close` — tells the server not to keep the connection open (HTTP keep-alive) waiting for more requests, so `recv()` behaves like a clean one-shot exchange
        - `\r\n` — HTTP's line ending (carriage return + newline, not just `\n`)
- **`client.recv(4096)`**
    - Reads up to 4096 bytes back, as **raw bytes**. Google's real response is likely bigger than 4096 bytes — a single `recv()` call may only capture part of it. (Next step: loop `recv()` until no more data comes, to capture the full response.)
- **`response.decode()`**
    - Converts raw bytes into a readable string (UTF-8 by default).
- **`client.close()`**
    - Releases the socket cleanly.

### Bug I hit - the `\r\n\r\n` issue

> [!bug] What went wrong Original attempt: `b"GET / Http/1.1\r\nHOST: google.com\r\n\n"` — this hung / returned nothing useful.

**Why it broke:**

1. `Http/1.1` should be `HTTP/1.1` — case matters to strict protocol parsers.
2. `\r\n\n` at the end should be `\r\n\r\n`. HTTP requires a **blank line** — two `\r\n` in a row — to signal "headers are done, this is the complete request." With only `\r\n\n`, the server keeps waiting for more headers that never arrive.

**The core lesson:** a raw TCP socket is just a pipe for bytes — it doesn't know or enforce HTTP. You can send _anything_ over it. But if you want a sensible reply, you have to speak the exact protocol the service on the other end expects. Send malformed input, and you get silence, a hang, or the connection gets dropped.

# UDP Client

> [!question] Goal Send a UDP packet to a local port and read back whatever comes in response.

```python
import socket

HOST = '127.0.0.1'
PORT = 9997

client = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)

client.sendto(b"AABBCCC", (HOST, PORT))

data, addr = client.recvfrom(4096)
print(data.decode())
client.close()
```

### Line-by-line

- **`socket.SOCK_DGRAM`** — UDP instead of TCP: connectionless, no handshake, no delivery guarantee. "Fire and forget."
- **`client.sendto(b"...", (HOST, PORT))`** — sends the bytes to the target address/port. Unlike TCP's `connect()` + `send()`, there's no handshake step — `sendto()` will return successfully **even if nothing is listening on the other end.** UDP has no way to know or care.
- **`client.recvfrom(4096)`** — waits for a reply, returning both the data and the sender's address (`addr`). This will **hang indefinitely** if nothing ever replies, since there's no timeout by default.

### Testing it without writing a full UDP server

Used netcat as a stand-in listener instead of building a Python server first:

```bash
nc -u -l -p 9997
```

- `-u` → UDP mode
- `-l` → listen mode
- `-p 9997` → port to listen on

**How the test actually worked:**

1. Ran `nc -u -l -p 9997` in one terminal.
2. Ran the Python client in a second terminal.
3. `AABBCCC` appeared in the netcat terminal — proof the packet arrived.
4. Netcat doesn't auto-reply — had to manually type a message and hit enter for anything to be sent back.
5. Only then did `recvfrom()` in the Python script unblock and print what was typed.

**Why this matters, concretely:** netcat could have not been running at all, and step 2 (`sendto`) would have completed with zero errors regardless. There is no built-in way for the sender to know if a UDP packet was received. That's the "fire and forget" nature of UDP, made real instead of a line in the Networking notes — TCP's handshake is exactly the thing UDP skips.

# TCP Server

> [!question] Goal Build a server that listens on a port, accepts a connection, receives data, and sends a reply — the other half of the TCP client above.

```python
import socket

IP = "0.0.0.0"
PORT = 9998

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)  # 1. create socket object
server.bind((IP, PORT))                                      # 2. bind to address + port
server.listen(5)                                              # 3. start listening
print(f"[*] Listening on {IP}:{PORT}")

client_socket, client_address = server.accept()               # 4. accept a connection (blocks)
print(f"[*] Accepted connection from {client_address[0]}:{client_address[1]}")

request = client_socket.recv(4096)                            # 5. receive data
print(f"[*] Received: {request.decode()}")

client_socket.send(b"ACK from server!")                       # 6. send a reply

client_socket.close()                                          # 7. clean up
server.close()
```

### Line-by-line — what's different from the client

1. **`socket()`** — identical to the client, just creating the raw socket object.
2. **`bind((IP, PORT))`** — server-only step. Claims a specific port on this machine so the OS routes matching traffic here.
    - `0.0.0.0` = "listen on all network interfaces," not just localhost. Using `127.0.0.1` here would only allow connections from the same machine.
3. **`listen(5)`** — puts the socket into listening mode. `5` is the **backlog**: how many _pending_ connections can queue up before the OS starts rejecting new ones while the current one is being handled. Not a total connection limit.
4. **`accept()`** — the big conceptual jump from client code. **Blocks** until a client actually connects. Returns two things:
    - a _new_ socket (`client_socket`) specific to that one client
    - their address (`client_address`)
    - Mental model: the server splits into "the doorman" (`server` socket — just accepts new people) and "the conversation" (`client_socket` — one per person who walked in). The original `server` socket is still free to accept more connections.
5. **`client_socket.recv()`** — same idea as the client's `recv`, just called on the per-client socket.
6. **`client_socket.send()`** — reply back to that specific client only.
7. Close the per-client socket when done with them; close the `server` socket when shutting down entirely.

### Bug I hit - `0.0.0.0` in the client

> [!bug] What went wrong Reused `HOST = '0.0.0.0'` in the **client** script (copy-paste from the server) and tried `client.connect((HOST, PORT))`.

**Why it broke:** `0.0.0.0` is a _wildcard_ address - it only makes sense for a socket that's **claiming/binding** a port to listen on. It isn't a real, routable destination, so a client can't connect _to_ it (behavior is inconsistent across OSes — sometimes silently maps to localhost, sometimes fails outright).

**Fix:** client must point at `127.0.0.1` (or the real target IP), never `0.0.0.0`:

```python
HOST = '127.0.0.1'   # not 0.0.0.0
```

**Rule of thumb going forward:** `0.0.0.0` → only ever appears in `bind()` on the listening side. `127.0.0.1` / a real IP → always what a client connects to.

### `[*]` notation

Not a Python feature - just literal text inside the f-string, a common status-prefix convention seen throughout security tooling (Metasploit, exploit scripts, scanners):

- `[*]` → general info/status
- `[+]` → success
- `[-]` → failure
- `[!]` → warning

Purely a human-readability habit — deleting it changes nothing functionally.

## Applying this to real scanning (banner grabbing)

Once Nmap shows an open port, this exact TCP client pattern is how you probe it manually — this is what Nmap's `-sV` is doing under the hood.

```python
import socket

HOST = "192.168.10.124"
PORT = 62078

client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
client.settimeout(3)          # don't hang forever waiting for a banner
client.connect((HOST, PORT))

try:
    client.send(b"\r\n")
    response = client.recv(4096)
    print(response.decode(errors="replace"))
except socket.timeout:
    print("[-] No response within timeout — service may require a specific protocol message")
except ConnectionResetError:
    print("[-] Connection reset by peer — service rejected the input")

client.close()
```

**Real result hit:** connecting to a `tcpwrapped` port (62078, likely Apple's `lockdownd`) and sending `b"\r\n"` produced `ConnectionResetError: [Errno 104] Connection reset by peer`.

**What that means:** the handshake succeeded and the send went through, but the service read the bytes, decided they weren't valid input for its protocol, and sent a **RST (reset)** packet — an abrupt forced teardown. Different from:

- a **timeout** (nothing happens, no response at all)
- a **clean close** (service replies then politely ends the connection)

A reset in response to junk input is itself a fingerprinting signal — it tells you the service has protocol-aware input validation, rejecting anything that doesn't match its expected format immediately, rather than ignoring it. Blind poking with plain text works fine against simple text-based services (SSH, FTP, plain HTTP banners) but fails against services expecting a strict/binary protocol (like lockdownd's length-prefixed binary plist handshake).

## Summary - client vs server, TCP vs UDP

||TCP Client|TCP Server|UDP Client|
|---|---|---|---|
|Socket type|`SOCK_STREAM`|`SOCK_STREAM`|`SOCK_DGRAM`|
|Connection step|`connect()`|`bind()` + `listen()` + `accept()`|none — connectionless|
|Handshake|Yes (SYN/SYN-ACK/ACK, automatic)|Yes (same handshake, server side)|No handshake at all|
|Delivery guarantee|Reliable, ordered|Reliable, ordered|None — fire and forget|
|Send|`send()`|`client_socket.send()`|`sendto()` (needs address each time)|
|Receive|`recv()`|`client_socket.recv()`|`recvfrom()` (returns data + sender address)|
|Failure if target is down|`connect()` raises an error|N/A|`sendto()` succeeds anyway — no way to know|

# Replacing Netcat with Python

> [!info] Why this exists Netcat is called "the hacker's Swiss Army knife" because it does a handful of things constantly needed during recon/exploitation: connect out, listen for connections, pipe data through a running command, move files over a raw socket. The problem: real netcat isn't always installed on a target, and command-execution builds (`-e`) are often stripped out or watched for by defenders. Building a minimal clone means you're never dependent on a tool that might not be there — and you understand exactly what it's doing, because you wrote it.
> 
> This is also the direct bridge from "TCP client/server" to **bind shells and reverse shells** — same socket pattern, with `subprocess` swapped in for a hardcoded reply.

---

## What netcat actually does, broken into pieces

Before building the clone, it helps to separate netcat's core features, since the Python version maps one-to-one:

|Netcat feature|Netcat flag|Python equivalent|
|---|---|---|
|Connect to a remote host/port|(default / `nc host port`)|`socket.connect()` — your TCP client|
|Listen on a port for connections|`-l -p PORT`|`socket.bind()` + `listen()` + `accept()` — your TCP server|
|Run a command and pipe its I/O through the connection|`-e /bin/bash`|`subprocess` module|
|Send a file over the connection|shell redirection (`nc < file`)|reading file bytes, `send()`-ing them|

The Python clone is really just: **your existing TCP client/server code, plus one new piece — `subprocess`, wired into `send()`/`recv()` instead of a hardcoded message.**

---

## The new piece: `subprocess`

This is the only genuinely new concept here — everything else is socket code you've already built.

python

```python
import subprocess

output = subprocess.check_output("whoami", shell=True, stderr=subprocess.STDOUT)
print(output.decode())
```

- **`subprocess.check_output(...)`** — runs a shell command and captures whatever it _would have printed to the terminal_ as bytes, instead of letting it print directly.
- **`shell=True`** — runs the command through the system shell (e.g. `/bin/sh`), which means things like pipes (`|`), `&&`, and environment expansion work, same as typing it in a terminal. (Security note: `shell=True` is exactly what makes command injection possible if the input isn't trusted — worth remembering for later when you're on the _defensive_ side of this.)
- **`stderr=subprocess.STDOUT`** — merges error output into the same stream as normal output, so you capture everything the command produced, not just the success case.
- **`output`** comes back as bytes (same as everything from a socket) — hence `.decode()` to read it.

**The conceptual leap:** in your TCP server, you had:

python

```python
client_socket.send(b"ACK from server!")
```

A netcat-style listener instead does:

python

```python
command = client_socket.recv(4096).decode()
result = subprocess.check_output(command, shell=True, stderr=subprocess.STDOUT)
client_socket.send(result)
```

Instead of a hardcoded reply, **whatever the client sends is treated as a shell command, run locally, and the output is sent back.** That one substitution is what turns "a server that echoes text" into "a server that gives someone remote command execution." This is the exact mechanism behind a bind shell.

---

## Building the listener (bind-shell-style netcat replacement)

> [!question] Goal A server that listens on a port, and whatever text a connecting client sends, it runs as a shell command and sends the output back — repeatedly, not just once.

python

```python
import socket
import subprocess

IP = "0.0.0.0"
PORT = 9999

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
server.bind((IP, PORT))
server.listen(5)
print(f"[*] Listening on {IP}:{PORT}")

client_socket, client_address = server.accept()
print(f"[*] Accepted connection from {client_address[0]}:{client_address[1]}")

while True:
    command = client_socket.recv(4096).decode().strip()

    if not command:
        continue
    if command.lower() in ("exit", "quit"):
        print("[*] Client requested exit — closing connection")
        break

    try:
        output = subprocess.check_output(
            command, shell=True, stderr=subprocess.STDOUT
        )
    except subprocess.CalledProcessError as e:
        # command ran but returned a non-zero exit code (e.g. file not found)
        output = e.output

    client_socket.send(output)

client_socket.close()
server.close()
```

### What's new here vs. your earlier TCP server

- **`while True:` loop around `recv`/`send`** — your original TCP server handled exactly one message, then closed. A netcat replacement needs to keep the connection open and handle _many_ commands in sequence, like a real shell session. This is the same conceptual jump as "one request" → "ongoing conversation."
- **`.strip()`** — command input over a socket often comes with trailing `\r\n` or `\n` (especially if the client is netcat itself, or a terminal that adds a newline on Enter). `strip()` removes that so `"whoami\n"` doesn't confuse the shell.
- **`if not command: continue`** — guards against empty `recv()` calls (e.g. a stray newline) from crashing `subprocess` on an empty string.
- **`exit` / `quit` check** — a clean way to end the session on command, rather than only being able to kill it by closing the socket from the client side.
- **`try/except subprocess.CalledProcessError`** — this is the fix for a real gap: `subprocess.check_output` **raises an exception** if the command exits with a non-zero status (e.g. `cat nonexistent_file`), rather than just returning the error text like a real terminal would show you. Without catching this, one bad command would crash the whole listener. `e.output` still contains whatever error text the command produced before failing, so you can send that back instead of losing the connection.

---

## Building the client side (talking to your own listener)

This is just your existing TCP client script, aimed at the new listener port, but built as a loop so you can keep sending commands:

python

```python
import socket

HOST = "127.0.0.1"
PORT = 9999

client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
client.connect((HOST, PORT))

while True:
    cmd = input("shell> ")
    client.send(cmd.encode())

    if cmd.lower() in ("exit", "quit"):
        break

    response = client.recv(4096)
    print(response.decode(errors="replace"))

client.close()
```

- **`input("shell> ")`** — takes a command from you, the operator, at the keyboard.
- **`cmd.encode()`** — the reverse of `.decode()`. Turns your typed string into bytes to send over the socket (sockets only move bytes, never plain strings).
- **`errors="replace"`** on decode — some command output (e.g. binary data, unusual characters from certain tools) might not cleanly decode as UTF-8. `errors="replace"` swaps anything invalid for a placeholder character instead of crashing the script outright — useful defensive habit once you're pointing this at real, unpredictable targets rather than your own machine.

### Testing it

1. Run the listener script — it prints `[*] Listening on 0.0.0.0:9999` and blocks on `accept()`.
2. Run the client script in a second terminal — connects immediately.
3. Type a command at the `shell>` prompt (e.g. `whoami`, `pwd`, `ls`) — it's sent to the listener, executed there, and the output is sent back and printed.
4. Type `exit` to cleanly close both sides.

---

## Why this matters (tying it back)

- **This is a bind shell**, in its simplest form: a listener sitting on a port, waiting for a connection, that will run whatever commands it's sent. The only difference from a "real" bind shell payload is that this one is deliberately simple and interactive rather than hidden/obfuscated.
- **A reverse shell** is the same idea with the roles flipped: instead of the target _listening_ and you _connecting to it_ (which requires the target to have an open, reachable port — often blocked by firewalls/NAT), the target _connects out_ to a listener _you_ control. That's just swapping which script does `bind()+listen()+accept()` and which one does `connect()` — same building blocks, different direction.
- **Why build this instead of just using real netcat:** now you know _exactly_ what's happening at each step — no `-e` flag magic, no wondering what a prebuilt binary does under the hood. If a target doesn't have netcat installed but does have Python, you can write (or paste) something like this listener directly.

> [!warning] Only run this against your own machines/lab environment. Same rule as everything else — Bandit, THM, HTB, home lab. A listener that executes arbitrary shell commands is, by definition, exactly the kind of thing that must never run on a system you don't own or have explicit permission to test.

## The setup

- **Ubuntu VM** — runs the listener script from the netcat-replacement notes. Binds to `0.0.0.0:9999`, blocks on `accept()`, waiting.
- **Arch host** — runs the client script, but pointed at the **VM's actual IP address**, not `127.0.0.1`.

> [!note] Why not `127.0.0.1` here `127.0.0.1` (localhost) only works when client and server are on the **same machine**. Once the listener is on a separate VM, the client needs the VM's real network address to reach it.

**Finding the VM's IP:** run `ip a` **inside the Ubuntu VM** — look for something like `192.168.x.x` (assuming NAT or bridged networking). This is the address to put in the client's `HOST` variable.

This is a legitimate, safe way to test this — both machines are mine, so this is a proper home lab exercise, not something to hesitate over.

---

## What actually happens when it connects

Real command execution on the Ubuntu VM, run **as whatever user started the listener script**:

- `whoami` from the Arch client → returns the VM's username
- `ls`, `cat /etc/passwd`, `ip a`, etc. → all executed on the VM, output sent back over the socket and printed on Arch

This is genuinely "access to the system" in the same sense a real bind shell payload gives an attacker — not a simulation of it.

---

## The privilege ceiling — access ≠ full control

> [!warning] Important distinction Whatever comes back through the shell only has the **privileges of the user who started the listener script.** If the listener was started as a normal (non-root) user, the "shell" I get is equally limited — same restrictions that user would normally have:
> 
> - Can't read root-only files
> - Can't install packages
> - Can't touch other users' data

**"I have a shell" and "I have root" are two separate milestones.** Getting the initial shell is _initial access_. Going from a limited user to root (or another higher-privilege user) requires a separate skill: **privilege escalation** — misconfigured sudo rules, SUID binaries, kernel exploits, writable files owned by root, cron jobs running as root, etc. This is typically the _next_ stage after initial access in a real CTF or pentest, not something that comes for free with the shell itself.

---

## Experiment to run — proving the ceiling exists

1. Start the listener on the Ubuntu VM as a **normal user** (not with `sudo`).
2. Connect from Arch, confirm `whoami` shows the normal user.
3. Try `cat /etc/shadow` — should fail with **permission denied**.
4. Try `sudo whoami` — will either fail (no password given, non-interactive) or prompt for a password the script can't supply.

This turns "access ≠ full control" from an abstract statement into something directly observed — same idea as watching a UDP packet vanish with no confirmation, or watching lockdownd send a `RST` instead of a reply. The permission-denied error _is_ the lesson.

# Replacing Netcat v2 — CLI, Threading, File Upload

> [!info] Context Upgrade to [[Replacing_Netcat]] after comparing the first version against Black Hat Python's netcat chapter. The core socket logic is the same as before — this adds the pieces that make it a real, flexible tool instead of a fixed single-purpose script: a command-line interface, multi-client handling, file transfer, and a receive loop that actually captures full responses.

---

## What's new, at a glance

|Gap in v1|What v2 adds|
|---|---|
|Hardcoded HOST/PORT, one fixed behavior|`argparse` — one script, multiple modes via flags|
|Only handled **one** client, then stuck|`threading` — accept loop + a thread per client|
|Only ran shell commands|Also supports **file upload** as a mode|
|`shell=True` (injection-prone)|`shlex.split()` — parses command safely without invoking a shell|
|Single `recv(4096)` — could cut off large responses|A loop that keeps reading until a partial/empty chunk signals "done"|

---

## Piece 1 — `argparse`: turning this into a real CLI tool

Right now our scripts have `HOST = "127.0.0.1"` hardcoded at the top — fine for testing, useless as an actual tool, since you'd have to edit the file every time you wanted to point it somewhere else.

```python
import argparse

parser = argparse.ArgumentParser(description="Simple netcat-style tool")
parser.add_argument("-t", "--target", default="127.0.0.1", help="target IP")
parser.add_argument("-p", "--port", type=int, default=9999, help="target port")
parser.add_argument("-l", "--listen", action="store_true", help="listen mode")
parser.add_argument("-e", "--execute", help="command to execute on connection")
parser.add_argument("-u", "--upload", help="filename to save uploaded data as")

args = parser.parse_args()
```

- **`add_argument("-t", "--target", ...)`** — defines a flag with both a short (`-t`) and long (`--target`) form. `default=` is used if the flag isn't given at all.
- **`action="store_true"`** — for flags that are just on/off switches (no value needed). If `-l` is present, `args.listen` becomes `True`; otherwise `False`. Compare to `-t`, which expects a value after it (`-t 192.168.1.5`).
- **`args = parser.parse_args()`** — reads `sys.argv` (whatever was typed after the script name on the command line) and turns it into an object where `args.target`, `args.port`, `args.listen`, etc. hold the values.

Now the script can be run like:

```bash
python3 my_netcat.py -l -p 9999          # listen mode
python3 my_netcat.py -t 192.168.10.5 -p 9999   # client, connect out
```

**Why this matters beyond convenience:** this is the exact pattern real tools use — Nmap, Hydra, sqlmap, all of them parse flags this way. Learning `argparse` here means you can read _any_ of those tools' `--help` output and understand what's happening in their source when you eventually look.

## Piece 2 — `threading`: handling more than one client

Our v1 listener did this:

```python
client_socket, client_address = server.accept()   # blocks once
# ...handle that one client...
server.close()
```

Once one client connected, the listener was committed to _only_ that client. A second connection attempt would just sit waiting — `accept()` was already spent.

The fix: loop `accept()` forever, and hand each new connection off to its own **thread** so the main loop is immediately free to accept the next one.

```python
import socket
import threading

def handle_client(client_socket, client_address):
    print(f"[*] Accepted connection from {client_address[0]}:{client_address[1]}")
    # ... do the actual work with this client (command exec, upload, etc.) ...
    client_socket.close()

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
server.bind(("0.0.0.0", 9999))
server.listen(5)
print("[*] Listening on 0.0.0.0:9999")

while True:
    client_socket, client_address = server.accept()
    client_thread = threading.Thread(
        target=handle_client, args=(client_socket, client_address)
    )
    client_thread.start()
```

- **`while True: ... accept()`** — the listener never stops waiting for new connections; each call to `accept()` just picks up the _next_ one whenever it arrives.
- **`threading.Thread(target=..., args=...)`** — creates a new, separate thread of execution. `target` is the function to run _in_ that thread; `args` is the tuple of arguments to pass it. Nothing runs yet — this just builds the thread object.
- **`client_thread.start()`** — actually starts that thread running `handle_client(client_socket, client_address)` concurrently, while the main `while True` loop immediately goes back to `accept()` for the next connection.

**Mental model:** the main loop becomes purely "the doorman" — its only job is accepting new people and handing each one off to a dedicated helper (thread) to actually deal with. It never gets stuck talking to any single client.

## Piece 3 — Safer command execution: `shlex.split()` instead of `shell=True`

v1 used:

```python
subprocess.check_output(command, shell=True, stderr=subprocess.STDOUT)
```

`shell=True` runs the string through `/bin/sh`, which means shell metacharacters (`;`, `|`, `&&`, backticks) are interpreted — powerful, but also exactly how command injection works if this string ever came from an untrusted source you didn't fully control.

A safer approach:

```python
import shlex
import subprocess

def execute(cmd):
    cmd = cmd.strip()
    if not cmd:
        return ""
    try:
        output = subprocess.check_output(shlex.split(cmd), stderr=subprocess.STDOUT)
    except subprocess.CalledProcessError as e:
        output = e.output
    return output.decode(errors="replace")
```

- **`shlex.split("ls -la /tmp")`** → `["ls", "-la", "/tmp"]`. It splits a command string into a proper argument list the same way a shell _would_ parse it (respecting quotes, etc.), but **without actually invoking a shell**.
- Passing that list to `subprocess.check_output(...)` (no `shell=True`) means the OS runs `ls` directly with those exact arguments — there's no shell in between to misinterpret `;` or `|` as "run a second command." This closes off a real injection path.
- **Trade-off worth knowing:** this also means shell _features_ (pipes, redirection, `&&` chaining) won't work anymore, since there's no shell to interpret them — you only get single, direct commands. For a learning tool that's a fine trade; for something aiming to fully mimic a real shell session, this is a known limitation.

## Piece 4 — File upload as a third mode

Same `recv()`-loop pattern already familiar from command execution, just writing to a file instead of feeding a command:

```python
def handle_upload(client_socket, filename):
    file_bytes = b""
    while True:
        data = client_socket.recv(4096)
        if not data:
            break
        file_bytes += data

    with open(filename, "wb") as f:
        f.write(file_bytes)

    client_socket.send(f"Saved file as {filename}".encode())
```

- **`while True: recv()... if not data: break`** — keeps pulling chunks off the socket until the sender closes their end (an empty `recv()` result means "no more data is coming, connection closed"). This is the piece our v1 scripts didn't need, since they only ever expected one short message at a time.
- **`open(filename, "wb")`** — `"wb"` = write, binary mode. Important because file contents (unlike command output) might not be valid text at all — binary mode writes the raw bytes exactly as received, no decoding involved.

## Piece 5 — The receive loop gap: capturing responses bigger than 4096 bytes

This is the fix for something flagged back in the TCP client notes (`response = client.recv(4096)` might not capture all of Google's HTML). The real fix:

```python
def recv_all(sock, buffer_size=4096):
    response = b""
    while True:
        chunk = sock.recv(buffer_size)
        response += chunk
        if len(chunk) < buffer_size:
            break
    return response
```

- Keep calling `recv()` and appending each chunk.
- **The stopping condition:** if a chunk comes back _smaller_ than the buffer size you asked for, that's a signal there's nothing left to read right now — the sender's message was fully delivered. (Not a perfect signal for every protocol, but a solid, common heuristic for this kind of tool.)
- This replaces every single `client.recv(4096)` call from the earlier notes with something that won't silently truncate a large response.

## Putting it together — what "done properly" looks like

A complete version combines all five pieces: `argparse` reads the mode and target/port off the command line → if `-l`, run the threaded listener loop → each accepted client gets handed to `handle_client`, which checks whether it's an execute, upload, or interactive-shell request → commands run through `shlex.split()` instead of `shell=True` → all sends/receives use the `recv_all`-style loop instead of a single `recv(4096)`.
